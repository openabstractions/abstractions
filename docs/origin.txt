The seed / initial state. The original conversation that kicked this whole

THE PROBLEM
-----------

Goal: use my official deepseek.com API key from a desktop chat client.

First attempt: LM Studio.

  - LM Studio CAN host a local server (http://localhost:1234/v1) and serve
    models you've downloaded, via an OpenAI-compatible endpoint. api_key can
    be any string ("lm-studio").
  - But LM Studio CANNOT act as a client/frontend for a remote cloud API like
    api.deepseek.com. It only hosts local model files (.gguf).
  - Ollama cannot either. Both are strictly inference engines (backend), not
    chat clients for remote endpoints.
  - No PRs exist to change this — LM Studio is closed-source, and it goes
    against what both apps are fundamentally designed for.

The real distinction:
  - LM Studio / Ollama  = run model weights on YOUR CPU/GPU. Cannot reach out
    to a paid cloud endpoint.
  - Chatbox / Page Assist / LibreChat = empty visual UIs that just send text
    to your cloud account using your API key. They run no models.

ALTERNATIVES EXPLORED
---------------------

Dedicated API frontends (browser/desktop):
  - Chatbox (cleanest standalone desktop app, DeepSeek provider built in)
  - Page Assist (browser extension sidebar)
  - LibreChat / Chatbot UI (self-hosted web, ChatGPT-like)

Unified frontends (local + remote at the same time):
  - Open WebUI (browser-based, "king of the hill", open source)
  - AnythingLLM (desktop app, local engine + remote APIs)
  - Jan (LM Studio clone that ALSO supports remote APIs)


JAN
---

- Jan is the closest LM Studio clone: free, open source, all-in-one desktop
  app with built-in chat, local model downloader (Nitro engine), and remote
  provider settings.
- It runs local .gguf files exactly like LM Studio.
- It can connect remote providers: DeepSeek, OpenAI, Anthropic.
- Transfer LM Studio models by pointing Jan's Model Directory at:
    Windows: C:\Users\<You>\.lmstudio\models\
    Mac/Linux: ~/.lmstudio/models/
- Remote DeepSeek via Jan: Settings > Providers > DeepSeek > Enable > paste
  sk-... key.

Why Jan ended up being rejected:
  - Jan is a "Tier 1" chat wrapper. No file-system execution layer.
  - deepseek-reasoner + tools crashes it (see TOOL CALLING below).


PHYSICAL RESOURCES (THE "HIDDEN MESS")
--------------------------------------

Key insight: these local AI apps DO NOT negotiate with each other over
hardware. If LM Studio, Ollama, and Jan run at once, each blindly grabs
RAM/VRAM and they clash → slowdown, freeze, or OOM crash.

  - Models must load weight matrices into VRAM (GPU memory) to run fast.
  - An 8B model ≈ ~6GB of an 8GB GPU. A second engine sees 2GB left → fails
    or spills into system RAM (slow).
  - The OS is the ONLY "negotiator" — it grants or denies memory. Apps don't
    gracefully yield to each other.
  - Cloud API usage = 0% local GPU/VRAM. The client is a lightweight text
    messenger to DeepSeek's servers.
  - Rule: keep only ONE local engine active at a time.


OPENAI vs ANTHROPIC API (WHICH IS "MORE POWERFUL")
--------------------------------------------------

Neither is universally more powerful. Different philosophies.

OpenAI = the "Swiss Army knife" (multimodal):
  - Flagships: gpt-5.6-sol / o3-pro
  - Multimodal: text, image, voice, audio, video, TTS
  - Reasoning (o-series) for math/logic
  - Fine-tuning support
  - Batch API (50% off 24h queues)
  - Max context up to ~1,050,000 tokens

Anthropic = elite coding / reasoning / parsing:
  - Flagships: claude-fable-5 / claude-opus-5
  - Best-in-class coding (SWE-bench, repo management)
  - Prompt caching (up to 90% off repeated inputs)
  - Stronger instruction following / less hallucination
  - Text + image only; max context ~200,000 tokens

Verdict:
  - OpenAI → need voice, video, media gen, massive rate limits.
  - Anthropic → coding agents, scanning repos, reading large text.


DEEPSEEK EXPOSES BOTH FORMATS
-----------------------------

- DeepSeek's API is OpenAI-compatible AND Anthropic-compatible.
  - OpenAI format:  https://api.deepseek.com/v1
  - Anthropic format: https://api.deepseek.com/anthropic
- The Anthropic endpoint exists so devs can trick Claude Code (hardcoded to
  Anthropic's protocol) into using cheap DeepSeek models.
- For desktop UIs: ALWAYS use the OpenAI format.
- DeepSeek models:
  - deepseek-chat      = standard V3 text/coding model
  - deepseek-reasoner  = R1 reasoning model (emits hidden <think> chain)


TOOL CALLING (THE REAL PROBLEM)
-------------------------------

This is where Jan died and the whole direction changed.

Industry standard = OpenAI Function Calling (tool_calls). A model does NOT run
code — it outputs a formatted JSON object telling the client what to do:

  [User] -> [Client] -> [Model]
                          |  returns JSON "read_file('notes.txt')"
  [Executes] <- [Client] <- 

- DeepSeek DOES conform to the OpenAI tool_calls structure.
- BUT deepseek-reasoner emits a NON-STANDARD extra field, `reasoning_content`
  (its chain of thought), alongside the standard tool payload.
- DeepSeek's docs REQUIRE clients to preserve and echo back the exact
  reasoning_content block in history, or the next request fails with HTTP 400.
- Jan is a plain chat wrapper; it can't parse interleaved reasoning + tools →
  crash.
- Fix options:
  1. Use deepseek-chat (no reasoning block, standard format).
  2. Use a client built to re-inject reasoning_content (Open WebUI, LobeChat).

MCP (MODEL CONTEXT PROTOCOL)
----------------------------

The accepted standard for connecting any model (local or cloud) to tools/data.
Introduced by Anthropic, becoming universal and open source.

    [Client App] <--MCP--> [MCP Server] --> [Local Files / Git / Web / DB]

- Instead of each app writing custom file/terminal code, devs write tiny
  "MCP servers".
- Any MCP-supporting app + any model = secure access to local files, terminal,
  databases.


THE THREE TIERS
---------------

  TIER 1 — Chat wrappers (Jan, LM Studio, Chatbox)
      Pure text in/out. No file execution or tool sandbox.

  TIER 2 — Advanced web UIs (Open WebUI, LobeChat)
      Native tool/plugin support. Parse Python pipelines internally.

  TIER 3 — Agentic IDEs (Cursor, Windsurf, Cline, OpenCode)
      Full system read/write. Auto-edit files, run terminal commands.


OPEN WEBUI vs CURSOR/CLINE (WHICH "KING")
-----------------------------------------

Open WebUI ("King of chat/documents/tools"):
  - Local program (not a cloud site) — installs to your machine (Docker/
    desktop installer), serves a browser UI at localhost.
  - Built-in Python sandbox, Tools/Filters marketplace, native MCP support.
  - Workspaces / "Knowledge" folders → RAG (vector DB search over files).
  - Good for: reading/querying documents, general automation, web search.
  - NOT good for: deeply editing a whole code structure.

Cursor / Cline / OpenCode ("Kings of code"):
  - Live inside the editor. Scan the multi-folder project, watch terminal
    errors in real time, create/edit/test files autonomously.
  - Good for: software development.
  - Not for casual chat.

The "higher abstraction" gap (why RAG feels shallow):
  - RAG chops files into random text chunks, keyword-matches, feeds snippets
    back → model loses architecture/dependency sense.
  - High-level tools run an LSP (Language Server Protocol) / structural parser
    to map imports, class hierarchies, file pathways → true project context.


OPENCODE (THE ANSWER / THE GOLDMINE)
------------------------------------

- OpenCode = open-source AI coding agent (the app used on the Mac).
- Handles files via high-level abstraction (LSP mapping, not RAG).
- Multi-agent orchestration: /init sets up persistent state (e.g.
  .planning/STATE.md); splits work into Architect / Planner / Coder agents.
- BYOK — paste DeepSeek key via `/connect` (or desktop Settings), provider =
  OpenAI-Compatible, base URL https://api.deepseek.com, models deepseek-chat
  / deepseek-reasoner.
- License: MIT (see LICENSING).


LICENSING (CAN I BUILD ON THIS?)
--------------------------------

DO NOT TOUCH:
  - LM Studio = CLOSED source. No public repo. Decompiling/repackaging its
    server binary → copyright/IP lawsuit. (Only the IDEA of its model download
    is useful.)

FREE TO FORK (permissive MIT / Apache 2.0):
  - Ollama   = MIT. Copy, rename, resell.
  - Jan      = MIT. Clone, reskin, replace weak chat with real tools.
  - OpenCode = MIT. The GOLDMINE — steal LSP mapping, context injection,
    terminal execution logic.
  - llama.cpp = MIT. The core math engine under Ollama/Jan/LM Studio.

HIDDEN TRAPS:
  - Model weights licenses: Qwen/Llama = commercial OK, but some (e.g.
    Cohere Command R, CC-BY-NC) forbid commercial use.
  - Copyleft: GPL/AGPL = poison. One AGPL file forces your whole app open
    source. Stick to MIT/Apache 2.0 only.


MODEL DOWNLOADS (WHAT LM STUDIO ACTUALLY DOES)
----------------------------------------------

- LM Studio's "Discover" tab = a wrapper over the Hugging Face API, filtered
  for .gguf (and Apple MLX) files.
- Real source = Hugging Face. GGUF is the universal local format.
- Key quantizer accounts to pull from:
  - TheBloke (historic, nearly every old model)
  - Bartowski (most active, modern GGUF for every new release)
  - Unsloth / lmstudio-community (clean mapped GGUF)
- Easier path: bundle Ollama's library; `ollama run qwen2.5` auto-downloads
  the optimized model from Ollama's registry.
- Hugging Face GGUF Trending Directory = see what the community downloads now.


BIG PICKLE (WTB?)
-----------------

- "Big Pickle" (opencode/big-pickle) = OpenCode's free hosted cloud default
  model, served through their router ("OpenCode Zen").
- Exists so the app doesn't throw "no model found" on first launch.
- Free tier / feedback phase → prompt data may be logged to improve the model.
- Replace it with your own key via /connect to avoid phoning home.

----------------

- Direction: build a higher-abstraction tool suite on OpenCode + Jan/Ollama +
